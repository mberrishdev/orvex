# Agent session interfaces for Orvex

**Research accessed:** 2026-11-02  
**Scope:** Official public documentation for Codex, Cursor Agent CLI, and GitHub Copilot CLI ACP. This note compares documented interfaces; no agents were installed or benchmarked.

## Comparison

| Criterion | OpenAI Codex | Cursor Agent CLI | GitHub Copilot CLI ACP |
|---|---|---|---|
| **Lifecycle** | `codex app-server` is the application-facing persistent interface: clients start/resume threads, start turns, stream events, interrupt, and handle approvals. `codex exec` is positioned for bounded one-off/script/CI jobs. ([Codex integration guidance](https://developers.openai.com/blog/codex-as-a-platform)) | `agent acp` starts a stdio child process using JSON-RPC 2.0 and newline-delimited messages. The client initializes, authenticates, creates or loads a session, prompts, and can cancel. ([Cursor ACP docs](https://cursor.com/docs/cli/acp)) | `copilot --acp --stdio` starts a child process, or ACP can use TCP. stdio lifecycle follows the parent pipe; TCP persists until stopped. One stdio client; TCP can accept separate connections. ACP is public preview and may change. ([Copilot ACP docs](https://docs.github.com/en/copilot/reference/copilot-cli-reference/acp-server)) |
| **Interactive / noninteractive** | App-server is driven by a client protocol, suitable for Orvex-owned UI. `codex exec` is explicitly for noninteractive bounded tasks. ([Codex integration guidance](https://developers.openai.com/blog/codex-as-a-platform)) | ACP is explicitly intended for custom clients/integrations; standard terminal workflows use interactive `agent`. ACP also supports `agent`, read-only `plan`, and read-only `ask` modes. ([Cursor ACP docs](https://cursor.com/docs/cli/acp)) | ACP provides sessions and prompts without controlling the terminal UI; terminal-dependent slash commands/pickers are unavailable over ACP. ([Copilot ACP docs](https://docs.github.com/en/copilot/reference/copilot-cli-reference/acp-server)) |
| **Events / input** | Newline-delimited JSON over stdin/stdout. Documented flow includes `initialize`/`initialized`, `thread/start`, `turn/start`, streamed `item/agentMessage/delta`, `turn/completed`, and `thread/resume`; app-server also exposes interruption and approval requests. ([ChatGPT token-sharing app-server guide](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server), [Codex integration guidance](https://developers.openai.com/blog/codex-as-a-platform)) | JSON-RPC requests/notifications include streamed `session/update`, `session/request_permission`, `session/cancel`, and session new/load/prompt. Cursor documents extension methods for question/plan responses, todo updates, subagent task notifications, and generated-image notifications. ([Cursor ACP docs](https://cursor.com/docs/cli/acp)) | ACP messages use NDJSON. Client opens a session with working directory and optionally MCP servers, sends prompts, receives session updates, and answers permission requests. ([Copilot ACP docs](https://docs.github.com/en/copilot/reference/copilot-cli-reference/acp-server)) |
| **Approvals** | App-server supports configured sandbox and approval policies and lets the client handle approval requests. This maps to an Orvex approval UI, though policy design remains Orvex’s responsibility. ([Codex integration guidance](https://developers.openai.com/blog/codex-as-a-platform)) | ACP permission requests accept allow-once, allow-always, or reject-once. The client must answer or tool execution can block. The additional `cursor/create_plan` extension can request plan approval. ([Cursor ACP docs](https://cursor.com/docs/cli/acp)) | ACP supports permission requests/responses. Server-level tool allow/deny options apply to every session and cannot be changed by a connecting client per session. ([Copilot ACP docs](https://docs.github.com/en/copilot/reference/copilot-cli-reference/acp-server)) |
| **Authentication / install** | Open-source CLI/app-server must be available in the guest. OpenAI documents a ChatGPT-plan OAuth integration in which the host application supplies an access token as `ACCESS_TOKEN`, renews it, restarts app-server, then resumes by thread ID. This is one documented integration route, not proof that every Codex sign-in setup works headlessly. ([app-server token guide](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server)) | Install Cursor CLI (`agent`) in the guest. ACP advertises `cursor_login`; docs also list pre-authentication with `agent login`, `--api-key`/`CURSOR_API_KEY`, or `--auth-token`/`CURSOR_AUTH_TOKEN`. ([Cursor ACP docs](https://cursor.com/docs/cli/acp)) | Install Copilot CLI in the guest and authenticate with GitHub, or configure a BYOK provider; ACP supports both according to current docs. ([Copilot ACP docs](https://docs.github.com/en/copilot/reference/copilot-cli-reference/acp-server)) |
| **Orvex guest-process fit** | **Recommended first adapter.** Persistent product-oriented protocol, threads, event stream, interrupt and approvals align with the planned Orvex session panel and lifecycle. Run app-server in the guest with the repo as cwd; Orvex’s guest supervisor owns its process and forwards protocol messages to the host UI. | **Strong ACP alternative, likely next adapter.** It offers the same core stdio session, event, cancel, and permission-request shape, plus Cursor-specific UX extensions. Compared with Copilot ACP, Cursor's current page does not label ACP preview; validate versioning and extension fallback behavior. ([Cursor ACP docs](https://cursor.com/docs/cli/acp), [Copilot ACP docs](https://docs.github.com/en/copilot/reference/copilot-cli-reference/acp-server)) | **Strong standards-based adapter.** ACP offers subprocess ownership, sessions, updates, and permissions, but GitHub explicitly marks its implementation public preview. Keep behind an adapter and recheck protocol/version stability. |

## Recommended first integration

Start with **Codex app-server inside the Linux guest**, supervised per workspace. Orvex should own the user-visible lifecycle: explicit Start Agent, prompt submission, streamed activity, approval presentation, interrupt, and resume. Save the provider thread ID with the Orvex workspace/session record. The host should communicate with a small guest-side supervisor rather than depend on a terminal UI or scrape terminal text.

Treat provider execution as a replaceable boundary in the Rust backend: a session manager owns process start/stop and durable Orvex session metadata; a provider adapter translates Codex messages/events into Orvex events; the frontend consumes provider-neutral events and sends prompts, approval answers, and interrupts. This is an architectural proposal, not an existing implementation.

For the next provider, evaluate **Cursor ACP** and **Copilot ACP** through the same provider-neutral ACP adapter. Cursor’s current CLI documentation exposes stdio JSON-RPC sessions, permission round-trips, cancellation, and useful extension methods. Copilot offers ACP as well, but its docs explicitly identify the implementation as public preview. Preserve unknown extension methods as optional capabilities so a baseline ACP client can still operate. Keep both provider CLI versions pinned during early integration and check advertised capabilities at startup.

## Orvex-specific security and product implications

- Start agent sessions only on explicit user action. A clone should not silently launch an agent that can modify files or run commands.
- Keep the agent process and its cwd inside the Linux guest. Do not pass host credentials into the guest by default. Provider login/token storage is an explicit product decision because the guest needs outbound network access for model requests.
- New workspace VMs get internet access only after the user approves it during creation, and that access remains enabled for the VM. Starting a cloud-backed agent should show that it inherits the workspace VM's network access; this is a consent gate, not a per-process firewall. The provider's authentication does not itself grant project-service access.
- A guest VM is an isolation boundary, not a guarantee that a coding agent’s changes are safe. Show tool activity and approval requests, and preserve workspace snapshots/recovery before broadening unattended permissions.
- If several agents share one VM, their processes may still contend for CPU, memory, ports, and guest-level credentials. Per-workspace process supervision and resource limits are separate from provider protocol support.
- **Codex protocol maturity:** the local `/opt/homebrew/bin/codex` observed for this project reports version `0.166.0` and labels `app-server` `[experimental]`. That command-level label should be treated as a compatibility risk, not as evidence that every app-server capability is unsupported: OpenAI documents app-server as an application integration surface, while also marking particular protocol events as experimental. Pin builds, check protocol/version information at startup, and isolate provider parsing behind an adapter. ([Codex integration guidance](https://developers.openai.com/blog/codex-as-a-platform), [OpenAI note on experimental app-server events](https://developers.openai.com/blog/custom-code-review-rules-for-codex))

## Unknowns and proof-of-concept questions

1. **Codex auth in Orvex:** Which user sign-in path will Orvex support (ChatGPT OAuth, API key, or both), how will refresh tokens be stored on the host, and what is the supported guest token handoff/rotation contract? The cited OAuth guide requires host-managed renewal and app-server restart; validate this end-to-end before committing to UX.
2. **Codex protocol compatibility:** Pin a CLI build and verify that app-server message/event schemas, approval responses, cancellation, process restart, and `thread/resume` behave as needed. The open protocol may evolve; implement tolerant parsing and version checks.
3. **Guest supervisor reliability:** Test child-process crash detection, stdout/stderr separation, graceful interrupt, host app restart, guest stop/resume, and reconnection without losing Orvex’s session-to-thread mapping.
4. **Network policy:** Determine the narrowest useful network permission for inference and provider auth, and whether Orvex can expose a clear “agent has internet access” state separately from project service ports.
5. **ACP interoperability:** Cursor and Copilot both document ACP over stdio, but verify protocol-version negotiation, permission option semantics, session load behavior, cancellation, and optional extension handling against the exact CLI builds. Cursor documents nonstandard `cursor/*` extensions; Copilot's current docs identify its ACP implementation as preview.
6. **Copilot ACP configuration:** Confirm whether server-level tool filters are sufficient for Orvex; GitHub documents that these options are fixed for all sessions on that server.
7. **Installation/licensing/support:** Decide whether provider CLIs are user-installed, installed from Orvex setup, or provisioned per guest; verify platform and account terms for the intended distribution. This note does not establish product redistribution rights or a support matrix.
